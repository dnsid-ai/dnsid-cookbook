# Demo Bank (the protected origin)

A small read-only API with synthetic data, deployed behind the load balancer as the service the verifier protects. It has no dependencies beyond Node.js 24.22.3.

## Behavior

| Request | Response |
|---|---|
| `GET /accounts` with the identity context (below) | `200`, JSON: the caller's own synthetic accounts and `caller` (the two identity values it received) |
| `GET /accounts/<id>`, one of the caller's accounts | `200`, JSON: that `account` and `caller` |
| `GET /accounts/<id>`, any other account (another agent's, or none) | `403`, `{"error":"account_not_permitted"}` |
| `HEAD` on either | the same status and headers as `GET`, no body |
| `GET` or `HEAD` on either without the identity context, or with a malformed one | `403`, `{"error":"identity_context_required"}` or `{"error":"identity_context_invalid"}` |
| The identity context without the verifier's attestation of it: none, a forged or malformed one, or one more than 30 s old | `403`, `{"error":"identity_attestation_required"}`, `{"error":"identity_attestation_invalid"}` or `{"error":"identity_attestation_stale"}` |
| Any other method on either | `405`, `Allow: GET, HEAD`, `{"error":"method_not_allowed"}` |
| Any other path | `404`, `{"error":"not_found"}` |

The query string is ignored. Every response has `Cache-Control: no-store`. None of the data is, or is derived from, a
real person or account.

**Identity context:** exactly one `x-dnsid-verified-domain` and exactly one `x-dnsid-governance-id`, each a domain name
of at most 253 characters, and exactly one `x-dnsid-attestation` that the verifier made for those two values. The
verifier sets all three on a request it lets through, after removing any `x-dnsid-*` header the caller sent.

## What the identity headers do and don't prove

Their presence alone authenticates nothing: anyone who can reach this service directly can send them. So Demo Bank
accepts them only with the verifier's attestation: `x-dnsid-attestation: v1.<unix seconds>.<MAC>`, where the MAC is
the base64url HMAC-SHA256, under the deployment's key, of `dnsid-attestation v1`, the seconds, the verified domain and
the governance ID, one per line. It must be at most 30 s old and at most 5 s ahead of Demo Bank's clock. The key,
`DNSID_ATTESTATION_KEY` (32 to 256 characters from `A-Z a-z 0-9 - _`), is generated by Terraform for each deployment
and given to the verifier and Demo Bank only; both refuse to start without it. A caller without the key can't make an
attestation, so forged identity headers are refused here whichever way they arrive.

That matters because the load balancer is not a perfect gate: on a live deployment (2026-11-14), one of Google's front
ends forwarded a request to Demo Bank without evaluating the authorization policy, about 12 minutes after the policy was
created. The deployment still keeps other callers away, and the live tests check each of these (`deny-bypass-*`):

- Cloud Run ingress restricted to internal and Cloud Load Balancing traffic;
- the service's default `run.app` URL disabled;
- the authorization policy covering every forwarding rule in front of it.

`deny-forged-identity` opens Demo Bank's `run.app` URL for a moment and checks that forged identity headers, without
an attestation or with a forged one, are refused by Demo Bank itself.

A verified identity says who the agent is and who is accountable for it. It does not grant access to anyone's account:
an application decides that itself. Demo Bank's decision is its account policy (`accountsFor` in `server.ts`): each
verified domain maps to its own two synthetic accounts, derived from the domain name, so no list has to be configured
and no two agents share an account. An agent may list and read its own accounts and no other, whichever trusted
governance vouched for it.

## Logs

One JSON line per request on standard output:

```json
{"severity":"INFO","event":"origin_request","id":"<random UUID>","method":"GET","route":"accounts","status":200,"outcome":"served","verifiedDomain":"<domain>","governanceId":"<governance ID>"}
```

`method` is `GET`, `HEAD` or `other`; `route` is `accounts`, `account` or `other`; `outcome` is `served`,
`identity_missing`, `identity_malformed`, `attestation_missing`, `attestation_invalid`, `attestation_stale`,
`account_not_permitted`, `method_not_allowed` or `not_found`. The identity values appear only on a served request and on
an `account_not_permitted` refusal, never for an identity that wasn't attested. Raw headers, signatures, authorization
values, the attestation and its key, the path, the query string and error text are never logged.

## Running it

```sh
DNSID_ATTESTATION_KEY=<the verifier's key> PORT=8080 node origin/server.ts     # PORT defaults to 8080; listens on 0.0.0.0
```

A missing or malformed `DNSID_ATTESTATION_KEY`, an invalid `PORT` or a port that can't be bound ends the process with
exit code 1 and a fixed message on standard error (never the key).
`SIGTERM` or `SIGINT` stops accepting connections, lets requests in flight finish for up to 3 seconds, then closes every
connection and exits.

The container image is built from this directory (`docker build --platform linux/amd64 origin`); it runs as an
unprivileged user and contains only `server.ts`, `package.json` and `LICENSE`.
